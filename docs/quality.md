# Оценка качества

Требование ТЗ: точность извлечения фактов (цифры, даты, БИН) не ниже 85%.

## Набор вопросов

`eval_cases.json` — 67 вопросов, из них 46 на русском и 21 на казахском:

| Класс (инструмент) | Вопросов |
|---|---|
| ценовые аномалии | 12 |
| справедливость цены лота | 12 |
| сравнение цен между заказчиками | 10 |
| завышение объёмов | 9 |
| поиск закупок | 9 |
| аналитика закупок | 8 |
| карточка договора | 7 |

Наборы:
- **dev (46 вопросов)** — по ним агент дорабатывался;
- **holdout (21 вопрос)** — добавлялись после доработок, чтобы получить честную оценку на вопросах, под которые
  ничего не подстраивалось.

Вопросы составлены по реальным данным: реальные номера лотов (в том числе из нескольких пунктов плана),
договоров, коды ЕНС ТРУ, организации по названию, БИН цифрами и ссылкой на портал, разные формулировки,
пороги и годы.

## Эталоны

В кейсе хранятся вопрос, ожидаемый инструмент и параметры, но **не числа**. `run_eval.py` на каждом прогоне
заново считает эталон на Python по определениям метрик из [analytics.md](analytics.md):
- данные берутся из таблиц `mv_price_base`, `plan_points`, `lots`, `contracts`, `contract_items`, `mv_season`;
- **без** функций `tools.py` и **без** витрин `v_price_anomalies`, `v_volume_growth`, `mv_enstru_stats`.

Так eval проверяет и агента, и SQL-витрины независимой реализацией и остаётся валидным после обновления данных.

Эталонные факты по классам (всего 549):
- **аномалии:** число проверенных позиций, число аномалий, суммарная переплата, ID топ-3 договоров, цена,
  средневзвешенная, отклонение и переплата топ-1;
- **лот:** БИН заказчика, номер объявления, цена, P_base, N, n_город, Fair Price, отклонение, вердикт; для лота
  из нескольких пунктов — число пунктов, стоимость, отклонение лота, худший пункт;
- **объёмы:** число пар, отмеченные, БИН, код, количество, медиана, рост, сумма на прирост топ-1, коды топ-3;
- **сравнение:** N, медиана, средневзвешенная, число заказчиков, БИН и медиана самого дорогого и самого дешёвого;
- **аналитика:** число договоров, сумма, сумма и доля из одного источника, число поставщиков, крупнейший
  поставщик, крупнейший договор;
- **договор:** ID, дата, БИН поставщика, суммы с НДС и без, число редакций, способ закупки, статус;
- **поиск:** число лотов, сумма, крупнейший лот.

## Метрики

- **fact_recall** (основная): доля эталонных фактов, найденных во всём тексте ответа. Допуски:
  - сумма — ±0,5 тг или 0,05%;
  - доля — ±0,05 п. п.;
  - ID, БИН и даты — точное совпадение;
  - вердикт и название — на языке ответа.
- **route_acc:** верный инструмент и ключевые параметры. Ожидание «параметра быть не должно» тоже проверяется:
  ловит выдуманный год или БИН.
- **fact_precision:** доля чисел, дат и БИН в кратком выводе, подтверждённых данными (`verify`).

## Результаты

| Прогон | Вопросов | fact_recall | route_acc |
|---|---|---|---|
| dev, первый прогон, 14.10 | 30 из 40 (у 10 ошибка в коде eval) | 89,3% | 87% |
| **holdout, первый прогон** (12 вопросов) | 12 | **94,0%** | 100% |
| **договор и аналитика, первый прогон** (15 вопросов, из них 9 holdout) | 15 | **92,6%** (holdout-часть 88,4%) | 93% |
| весь набор после исправлений, хост, Ollama с Metal | 67 | 100% | 100% |
| весь набор, первый прогон в Docker (LLM в контейнере на CPU) | 67 | 98,0% | 100% |
| весь набор после исправлений, Docker | 67 | 100% | 100% |
| **итог 16.10, 02:27: финальный код (ИПЦ, вид предмета, очистка названий), хост** | 67 | **100%** (548 фактов) | **100%** |
| **итог 16.10, 02:39: тот же код, Docker** | 67 | **100%** (548 фактов) | **100%** |

В итоговых прогонах fact_precision 100%, 443 факта в кратких выводах. После загрузки ИПЦ изменились цены, и эталоны
пересчитались автоматически: число эталонных фактов стало 548 вместо 549, потому что изменился состав топа в одном
вопросе об аномалиях.

Один прогон в Docker был прерван и не учитывается. Модель на CPU при высокой нагрузке на машину упиралась
в тайм-ауты (180 с), клиент повторял запросы, и они копились. После этого добавлены потолок длины ответа модели
(`LLM_ROUTE_MAX_TOKENS=256`), один повтор вместо двух и `OLLAMA_NUM_PARALLEL=1`; итоговые прогоны в Docker
заняли 9,7 и 7,9 с на вопрос без тайм-аутов.

**Честная оценка — первые прогоны на вопросах, под которые агент не подстраивался: 88–94%.** Требование ≥ 85%
выполняется и на них. 100% получено после исправлений по найденным ошибкам, поэтому holdout больше не
«чистый». Перед сдачей полезно добавить новые вопросы и прогнать их один раз.

## Какие ошибки нашёл eval

| Ошибка | Где | Исправление |
|---|---|---|
| Лот из нескольких пунктов плана сравнивался по коду одного пункта с ценой другого (3 466 лотов) | `assess_lot_price` | оценка по каждому пункту, отклонение лота взвешено по количеству |
| КАТО `''` из лота у 17 579 пунктов плана — все считались одним «городом», ложный K_region | ETL | пустой КАТО не город, берётся адрес заказчика |
| Двойное округление: 37,9% вместо 37,8%, 73,3% вместо 73,2%, 6,2% вместо 6,3% | `tools.py` | доли до 6 знаков, Fair Price не округляется до расчёта |
| LLM подставляла год, top-K, код из примера в описании функции, товар «бумага», «баға», «услуги медицинские» | маршрутизация | параметры только из текста вопроса; товар должен начинать слово вопроса; служебные слова не считаются |
| Организация с общими словами («РГП на ПХВ», «МЦ») определялась неверно | маршрутизация | веса слов по редкости; при неоднозначности уточняющий вопрос |
| Номера лотов вида `33431522-ОЛ-ЗЦП1` не распознавались | регулярные выражения | исправлено |
| «яйца» не находило «Яйцо», «қағаз» (и «кaгaз» с латинской a) не находилось | поиск, справочник | стемминг, транслитерация, нормализация букв-двойников |
| Казахский вопрос об аналитике уходил в поиск | маршрутизация | переопределение типа по ключевым словам |

Две ошибки из таблицы нашлись только при прогоне в Docker: модель на CPU отвечала немного иначе, чем на Metal.
Вывод: перед сдачей eval нужно прогонять в той конфигурации, в которой агент будет работать.

## Что eval не покрывает

- Перефразировки за пределами набора, опечатки, длинные и составные вопросы (два заказчика или два года
  в одном вопросе).
- Уточняющие вопросы (случай «Автохозяйство») проверены вручную, в набор не включены.
- Смысловую правильность текста вывода на казахском носитель языка не проверял.
- Корректность самих определений метрик: эталон повторяет их, поэтому ошибку в определении eval не поймает
  (так сначала случилось с лотами из нескольких пунктов).

## Как запустить

```bash
python run_eval.py                         # все 67 вопросов, отчёт eval_report.md
python run_eval.py --split holdout         # только отложенные
python run_eval.py --only 9,18 -v          # отдельные вопросы с фактами
docker compose exec -T agent python run_eval.py   # в контейнере (LLM в контейнере)
python test_update.py                      # тесты инкрементального обновления (5)
```
