# Аналитика и метрики

Все расчёты выполняют SQL-витрины (`analytics.sql`) и функции `tools.py`. LLM ничего не считает: она только
выбирает функцию (см. [architecture.md](architecture.md#агент)). Цены — без НДС, за нормализованную единицу,
в тенге. Суммы договоров в аналитике закупок — с НДС.

Обозначения: «код» — код ЕНС ТРУ; сравнение цен всегда внутри пары (код, нормализованная единица);
`price_real` — цена позиции договора, приведённая по индексу потребительских цен (ИПЦ) к ценам последнего
месяца индекса (сейчас — сентябрь 2026). Все сравнения цен идут по `price_real`.

## Выбор методов

ТЗ допускает статистику (median, IQR, MAD, перцентили), unsupervised ML (Isolation Forest, LOF), правила
и нейросети. Использованы **статистика и правила**:

- **Статистика:** средневзвешенная, медиана, Q1/Q3/IQR, MAD, robust z-score, сезонный коэффициент по медиане
  отношений.
- **Правила:**
  - пороги отклонения (30%) и вердикты Fair Price (15% и 30%);
  - исключение услуг и работ;
  - минимальный размер выборки (N ≥ 5);
  - уровни уверенности.

Почему не Isolation Forest или LOF:

1. **Объяснимость.** ТЗ требует для каждого ответа метод, N и сравнение. «Цена выше средневзвешенной по 94
   позициям на 37,8%» проверяется руками по ссылкам; оценку аномальности из леса изолирующих деревьев
   проверить нельзя.
2. **Малые выборки.** Сравнение имеет смысл только внутри пары «код ЕНС ТРУ × единица». У 3 466 пар из 11 947
   N ≥ 5, у большинства — единицы и десятки позиций. На таких группах ML-детекторы нестабильны, а медиана
   и IQR работают.
3. **Воспроизводимость.** Тот же вопрос на тех же данных даёт те же цифры. Eval проверяет их независимым
   пересчётом.

Robust z-score и выход за Q3 + 1,5·IQR в ответах по аномалиям играют роль второго, устойчивого к выбросам
детектора рядом с основным правилом ТЗ (отклонение от средневзвешенной).

## 1. Ценовые аномалии (`find_price_anomalies`)

Вопрос: «закупки с отклонением цены > 30% от средневзвешенной по ЕНС ТРУ».

Для каждой пары (код, единица) по всем позициям всех заказчиков за 2024–2026 (`mv_enstru_stats`):

- средневзвешенная по количеству: `wavg = Σ(price_real · qty) / Σ qty`;
- медиана, Q1, Q3, `IQR = Q3 − Q1`, `MAD = медиана |price_real − медиана|`.

Для каждой позиции договора (`v_price_anomalies`):

| Показатель | Формула | Смысл |
|---|---|---|
| отклонение | `dev = (price_real − wavg) / wavg` | **аномалия, если `dev > порог`** (по умолчанию 0,30; порог можно задать в вопросе) |
| robust z-score | `(price_real − медиана) / (1,4826 · MAD)` | устойчивая к выбросам мера, для ранжирования и проверки |
| выход за забор Тьюки | `price_real > Q3 + 1,5 · IQR` | классический признак выброса |
| переплата | `(price_real − wavg) · qty` | сумма в тенге; по ней сортируется Top-K |

Фильтры:
- статистика считается только по кодам, где **N ≥ 5** позиций;
- услуги и работы исключены, если код не задан явно: «цена за единицу» у них равна цене всего договора
  и несравнима. Вид предмета берётся из поля API `RefSubjectType` пункта плана; если его нет (11 419 старых
  и восстановленных пунктов), то по единице измерения («Одна услуга», «Работа»). Правила расходятся всего
  в 27 случаях из 69 754.

На текущих данных (цены в ценах сентября 2026) проверено 52 935 товарных позиций, отклонение > 30% у 16 655 (31,5%), суммарная переплата 10,5 млрд тг.

## 2. Справедливость цены лота — Fair Price (`assess_lot_price`)

Вопрос: «адекватность цены лота № … относительно контрактов других ведомств в том же городе поставки».

Лот состоит из одного или нескольких пунктов плана (у 3 466 лотов их несколько, до 100). **Каждый пункт
оценивается отдельно:**

1. **Цена пункта.** Берётся из позиции договора по этому лоту: по `plan_point_id`, иначе по коду и единице.
   Если договора нет, цена = сумма пункта плана / количество.
2. **`P_base`** — медиана `price_real` по тому же коду и единице у **других ведомств** (заказчик лота
   исключён).
3. **`K_region = 1 + w · (медиана_город / P_base − 1)`**, где `w = n_город / (n_город + 5)`. Медиана по городу
   поставки сглаживается к 1 при малом числе наблюдений в городе: при 5 наблюдениях вес 0,5, при 20 — 0,8.
   Если в городе аналогов нет, `K_region = 1`, и ответ прямо об этом говорит.
4. **`K_season`** — коэффициент раздела КПВЭД (первые 2 знака кода) для месяца закупки (`mv_season`):
   - месяц — подписания договора или публикации объявления;
   - коэффициент = медиана отношения «цена / медиана своего кода» по позициям раздела в этом месяце;
   - считается при n ≥ 30 и ограничен диапазоном [0,8; 1,25], иначе 1.
5. **`Fair Price = P_base × K_region × K_season`**, отклонение `dev = (цена − Fair Price) / Fair Price`.
6. **Вердикт:**

   | Отклонение | Вердикт |
   |---|---|
   | \|dev\| ≤ 15% | в пределах рынка |
   | 15–30% | требует внимания |
   | > 30% | существенно выше (ниже) рынка |

**Лот целиком:**

`dev_лота = (Σ цена_i · кол-во_i − Σ FairPrice_i · кол-во_i) / Σ FairPrice_i · кол-во_i`

Сумма берётся по оценённым пунктам. В ответе также: сколько пунктов в каждом вердикте и пункт с наибольшим
отклонением.

**Инфляция.** Все цены приводятся к ценам последнего месяца индекса:
`price_real = цена · ИПЦ_последний / ИПЦ_месяца`, где месяц — дата подписания договора; для лота без договора —
дата публикации объявления.

- **Источник:** `cpi.csv`, помесячный ИПЦ Бюро национальной статистики АСПиР РК (% к предыдущему месяцу),
  январь 2024 — сентябрь 2026, 33 месяца. Ряд сверен с выпусками stat.gov.kz: совпадения по отдельным месяцам,
  годовая инфляция по 12 месячным значениям расходится с официальной не более чем на 0,2 п. п.
  (2024 — 8,7% против 8,6%, 2025 — 12,5% против 12,3%) из-за округления месячных значений до 0,1%.
- **Средний множитель:** для договоров 2024 года — 1,25, 2025 — 1,13, 2026 — 1,03.
- **Договоры после последнего месяца индекса** (октябрь 2026) не пересчитываются. Чтобы добавить месяц,
  достаточно дописать строку в `cpi.csv`; витрины пересчитаются при следующем обновлении.

В ответах таблица аномалий и Fair Price показывают цены в ценах последнего месяца, номинальная цена договора
указана в разделе 6.

## 3. Нетипичное завышение объёмов (`find_volume_spikes`)

Вопрос: «нетипичное завышение количества ТРУ по сравнению с предыдущими годами».

- `mv_volumes`: плановое количество и сумма по (заказчик, код, единица, год). Пункты плана с `removed_at`
  не учитываются.
- Для года `Y`: `медиана_прошлых = медиана количества за годы < Y` по той же тройке, `рост = кол-во_Y / медиана_прошлых`.
- **Нетипично**, если рост ≥ 2 раза (можно задать в вопросе: «в 3 раза») и сумма ≥ 1 млн тг.
- Сортировка по сумме, приходящейся на прирост: `сумма_Y · (1 − медиана_прошлых / кол-во_Y)`.
- В ответе: количества по годам, ID пунктов плана и ссылки на объявления, если пункт выставлялся на торги.

На текущих данных: 2026 год — проверено 7 021 пара (заказчик × код), отмечено 443; 2025 год — 5 905 и 412.

## 4. Сравнение цен между заказчиками (`compare_customers`)

- По одному коду ЕНС ТРУ, в **самой частой единице** этого кода. Позиции в других единицах перечисляются
  в ограничениях: сравнивать «пачку» с «коробкой» нельзя.
- По каждому заказчику: N, медиана, средневзвешенная, минимум, максимум, общее количество.
- «Самый дорогой» и «самый дешёвый» заказчики определяются только среди тех, у кого **N ≥ 3**: одна позиция
  не характеризует цену.

## 5. Аналитика закупок (`purchase_analytics`)

- Последние редакции договоров (доп. соглашения учтены), только в тенге, суммы с НДС. Год — по дате подписания.
- Показатели:
  - число договоров, сумма, средний договор;
  - число поставщиков и заказчиков;
  - разбивка по годам и способам закупки (с долями);
  - **доля закупок из одного источника** — способы «из одного источника по несостоявшимся закупкам»,
    «путём прямого заключения договора», в т. ч. по питанию (id 6, 23, 131);
  - крупнейшие поставщики, заказчики и коды;
  - крупнейшие договоры со ссылками.
- Если задан товар, суммы считаются по позициям договоров с этим кодом, а не по договорам целиком.

## 6. Карточка договора (`contract_lookup`) и поиск (`search_purchases`)

- **Карточка договора** — прямое чтение записи без расчётов: стороны, даты, суммы с НДС и без,
  способ закупки, статус, позиции, число редакций, первоначальная сумма. Номера договоров не уникальны
  (номер «1» встречается 435 раз), поэтому при нескольких совпадениях агент показывает кандидатов и просит
  уточнить заказчика.
- **Поиск** — по корням слов запроса в названии и описании лота; все слова должны встретиться. Повторные
  публикации одного пункта плана схлопываются до последней. Казахский запрос переводится через справочник
  ЕНС ТРУ (`name_kz` → `name_ru`).

## 7. Уверенность

| Тип | Высокая | Средняя | Низкая |
|---|---|---|---|
| Аномалии, сравнение | N ≥ 20 | N ≥ 5 | иначе |
| Пункт лота | N ≥ 20, n_город ≥ 3 и аналоги минимум от 3 ведомств | N ≥ 5 | иначе; **всегда низкая, если аналоги только от одного ведомства** |
| Лот целиком | преобладающая по пунктам; на уровень ниже, если оценено меньше половины пунктов | | |
| Объёмы | — | проверено ≥ 20 пар | иначе (история максимум 2 года) |
| Аналитика, карточка договора | прямой подсчёт, высокая | | |

Уровень уверенности и все ограничения метода выводятся в разделе 5 каждого ответа вместе с датой
актуальности данных.

## 8. Объяснимость и проверка чисел

Каждая функция возвращает JSON:
- `params` — какие фильтры применены;
- `method` — формула;
- `summary` — N и итоги;
- `results` — строки с ID и прямыми ссылками на портал;
- `limitations` — ограничения;
- `confidence` — уровень уверенности.

Ответ из 6 пунктов собирается из этого JSON кодом. Краткий вывод дополнительно проверяется функцией
`verify`: каждое число, дата и БИН должны встречаться в JSON (подробности в
[architecture.md](architecture.md#проверка-чисел)). Ссылки на портал:
- договор: `https://goszakup.gov.kz/ru/egzcontract/cpublic/show/{id}`;
- объявление: `https://goszakup.gov.kz/ru/announce/index/{id}`.
