# Риски и ограничения

Каждый ответ агента перечисляет ограничения своего метода в разделе 5. Здесь — общий перечень по проекту.

## Данные

| Риск / ограничение | Влияние | Что сделано / что делать |
|---|---|---|
| **Индекс планов OWS теряет записи без флага удаления**: 8 412 пунктов 2026 года за первую выгрузку, ещё 4 869 за сутки; по id API их тоже не отдаёт | если считать их удалёнными, объёмы 2026 года занижаются на 17–23% у крупных заказчиков | пропавшие пункты хранятся в последней известной версии, в журнале качества `missing_from_api` (10 969 на 16.10; часть пропавших пунктов возвращается в API). Риск обратный: настоящее удаление пункта без флага тоже не будет учтено. Нужно выяснить у оператора портала, как удаляются пункты плана |
| **Инфляция учитывается общим ИПЦ**, а не индексом цен конкретной товарной группы; ряд взят из агрегатора (finratings.kz по данным Бюро нацстатистики) и сверен с официальными выпусками | для товаров, цены на которые росли быстрее или медленнее общего ИПЦ, поправка неточна; месячные значения округлены до 0,1% | индекс сверен с stat.gov.kz (годовая инфляция — в пределах 0,2 п. п.); `cpi.csv` дополняется каждый месяц вручную, иначе договоры после сентября 2026 не пересчитываются. Улучшение: индексы по группам товаров и автоматическая загрузка с stat.gov.kz |
| **Широкие коды ЕНС ТРУ неоднородны** («Программное обеспечение», «Набор реагентов»: в наборе может быть разное число тестов) | 31,5% товарных позиций выше средневзвешенной больше чем на 30%; много шума в аномалиях и Fair Price | в ответе есть robust z, выход за IQR, N и уверенность. Улучшение: ранжировать по robust z или сравнивать с медианой, учитывать фасовку из описания |
| **Мало аналогов**: у многих кодов аналоги только у 1–2 ведомств | Fair Price статистически слабый | уверенность «низкая», если аналоги только от одного ведомства; N и число ведомств показываются |
| **Город поставки неточен**: у 58% пунктов плана нет КАТО в самом плане | K_region считается по городу лота или адресу заказчика | источник указывается (`kato_source`); у всех пунктов город определён |
| **2 295 позиций договоров без пункта плана** | не участвуют в ценовой аналитике (нет единицы измерения) | журнал `no_plan_point_unit_unknown`; 11 954 нужных пунктов плана API не отдаёт |
| **История только 2024–2026** | для объёмов максимум 2 прошлых года, медиана по 1–2 точкам | уверенность объёмов «средняя»; в ответе есть количества по годам |
| **Плановые, а не фактические количества** в анализе объёмов | план мог корректироваться, рост может быть обоснован | ограничение выводится в каждом ответе; нужна ручная проверка |
| **Услуги и работы**: «цена за единицу» = цена договора | несравнимы между договорами | по умолчанию исключены из аномалий и объёмов |
| **Поиск по корням слов** | ложные совпадения: «дизельное топливо» находит «фильтр топливный для дизельного двигателя»; синонимы не учитываются | поиск — вспомогательный инструмент; аналитика по товару идёт через код ЕНС ТРУ |
| **Номера договоров не уникальны** (номер «1» — 435 раз) | неоднозначный ответ на «договор № 1» | агент показывает кандидатов и просит уточнить заказчика |
| **1 договор в USD** | не входит в суммы аналитики | указано в ограничениях |

## Агент и LLM

| Риск | Влияние | Что сделано |
|---|---|---|
| Модель 7B «додумывает» параметры (год, БИН, код, товар) | неверные фильтры при правильном типе вопроса | параметры только из текста вопроса; проверка организации и товара; eval проверяет «лишние» параметры |
| Модель путает подписи чисел в связном тексте | правдоподобный, но неверный вывод | вывод собирается по шаблону; режим LLM-вывода выключен |
| Поведение модели зависит от среды (CPU в Docker против Metal) | на CPU нашлись две ошибки, которых не было на хосте | eval прогнан в Docker; прогонять в целевой конфигурации |
| Проверка чисел покрывает только краткий вывод | — | разделы 2–6 формируются из JSON кодом, без LLM |
| Скорость на CPU: 4–11 с на вопрос, до 130 с при загрузке модели (разово до 290 с после перезапуска); при высокой нагрузке на машину запросы упирались в тайм-аут 180 с и копились из-за повторов | медленные ответы; на тайм-ауте вопрос уходит в запасной классификатор по ключевым словам | `OLLAMA_KEEP_ALIVE=-1`, `OLLAMA_NUM_PARALLEL=1`, потолок длины ответа модели (`LLM_ROUTE_MAX_TOKENS`), один повтор вместо двух; для эксплуатации нужен GPU (в `k8s/ollama.yaml` предусмотрено) |
| Казахские тексты не проверены носителем языка; названия организаций и товаров в казахских ответах — на русском | качество казахского текста | шаблоны и переводы ограничений сделаны вручную; названия способов и статусов из справочника API |
| Составные вопросы (два заказчика, два года), поставщик по названию, фильтр по городу не поддерживаются | агент отвечает на часть вопроса | для расширения нужны новые функции в `tools.py` |

## Эксплуатация

| Риск | Что сделано / что нужно |
|---|---|
| Зависания API OWS: договоры одного БИН выгружались 8 725 с | повторы запросов с таймаутом 120 с; общего ограничения времени на сущность нет. В k8s задание ограничено 6 ч (`activeDeadlineSeconds`) |
| Неполная выгрузка удалит данные из базы | защита `MassDeleteError` (> 10% строк таблицы); сработала на реальном случае с планами |
| Сбой посреди обновления | одна транзакция ETL + витрины + водяные знаки; при ошибке откат, `etl_runs.status = failed`, следующий запуск забирает то же окно |
| Во время ETL запросы агента ждут 25–30 с | приемлемо при запуске раз в 6 ч; можно перенести на ночь |
| Токен API | в образ не попадает (`.dockerignore`), в git не попадает (`.gitignore`), передаётся только сервису обновления; в k8s — Secret |
| Нет авторизации на `/ask`, TLS, NetworkPolicy, мониторинга, резервного копирования по расписанию | **не сделано**; для эксплуатации обязательно. Ручная копия базы: `backups/` |
| Манифесты Kubernetes не проверены на кластере | проверена только сборка `kubectl kustomize` |
| Сырые данные — единственный источник для пересборки базы | хранятся в томе или PVC; 8 598 пунктов плана, которых нет в API, восстановлены из базы (`_recovered_from_db`) — их нужно резервировать вместе с базой |
| Время в контейнере БД в UTC, обновление пишет местное время (Asia/Almaty) | все отметки обновления пишет Python; `TZ` задан в образе и манифестах |
